# ADR 0005 — Authentication: JWT Access Tokens + Database-Backed Refresh Tokens

**Status:** ACCEPTED

## Context

CLAUDE.md section 12 requires revocation capability for compromised sessions and suspended
accounts. Authentication must be verified server-side. Client-supplied identity must never
be trusted.

## Decision

**JWT access tokens (short-lived, stateless) paired with opaque database-backed refresh
tokens (long-lived, rotated on each use, revocable by deletion).**

### Access token

- Algorithm: HS256
- Lifetime: 15 minutes
- Signing secret: from environment variable (`JWT_SECRET`), minimum 32 bytes, validated at startup
- Claims:
  - `sub` — user UUID v7 (string)
  - `iat` — issued-at timestamp (Unix seconds)
  - `exp` — expiry timestamp (Unix seconds)
  - `jti` — UUID v4 (for audit; not a foreign key to any table)
- No role claims in the token. Authorization checks query the database to avoid stale roles.

### Refresh token

- A cryptographically random 32-byte value generated by `crypto/rand` in Go.
- The raw token value is returned to the client exactly once (at login or refresh).
- Only the SHA-256 hash of the token is stored in the `sessions` table. The raw value is
  never persisted.
- Lifetime: 30 days from issuance.
- Rotation: a new refresh token is issued on every successful `/auth/refresh` call. The
  previous session row is updated with the new hash in the same database transaction.
- Revocation: `POST /api/v1/auth/logout` deletes the session row. The session is
  immediately invalid.
- Suspension: checking `users.is_suspended` at login and at every refresh call prevents
  suspended users from obtaining new tokens.

### Sessions table

The `sessions` table stores refresh token state:

- `id` — UUID v7 primary key (session identifier, not the `jti`)
- `user_id` — foreign key to `users.id`
- `token_hash` — SHA-256 hash of the opaque refresh token
- `expires_at` — `TIMESTAMPTZ`
- `created_at` — `TIMESTAMPTZ`
- `last_used_at` — `TIMESTAMPTZ` (updated on each successful refresh)
- `ip_address` — `TEXT` (for audit; nullable)
- `user_agent` — `TEXT` (for audit; nullable)

The `sessions.id` (UUID v7) and the JWT `jti` (UUID v4) are separate values with separate
purposes. `jti` is an access token audit identifier. `sessions.id` is the durable session
row key. They are never compared or joined.

### Flutter token storage

- Access token: held in-memory (BLoC state). Not written to disk.
  On app restart, the refresh token is used to obtain a new access token before
  rendering protected screens.
- Refresh token: stored in `flutter_secure_storage` (iOS Keychain / Android Keystore).

### Auth middleware (Go)

- Parses and verifies the JWT signature and `exp` claim on every protected request.
- Extracts `sub` and sets the user UUID in the request context.
- No database query per request for the access token (stateless verification).
- Protected handlers read the user ID exclusively from the request context. They never
  accept identity from the request body or query parameters.

### Rate limiting

Login and registration endpoints are rate-limited by Redis-backed counters. When Redis is
unavailable, these endpoints must **fail closed** (return HTTP 503) because they are
security-sensitive. See ADR 0006 and the rate limiting implementation for details.

## Alternatives considered

**Pure stateless JWT with no refresh or revocation.**
Rejected. A compromised access token cannot be invalidated before expiry. A suspended user
could continue using the API for up to 15 minutes.

**Redis-backed session tokens (fully stateful).**
Rejected. Creates a hard Redis dependency on every authenticated request. Redis unavailability
would take down authentication entirely, which is worse than a 15-minute window on access
tokens. The hybrid approach (stateless access + DB-backed refresh) is more resilient.

**RS256 (asymmetric JWT signing).**
Deferred. RS256 is appropriate when multiple independent services need to verify tokens
without sharing a secret. In Phase 1 there is one service. RS256 can be introduced in a
future ADR if a multi-service architecture is adopted.

**Longer-lived access tokens (e.g., 1 hour or 24 hours).**
Rejected. Longer lifetimes increase the blast radius of a stolen token since revocation
is not possible within the access token lifetime.

## Consequences

- The `sessions` table must be created in Phase 1 migrations before auth handlers are implemented.
- The JWT signing secret must be provided as an environment variable and validated at startup.
- The Flutter auth interceptor must handle 401 responses by attempting a silent refresh
  before propagating the error to the UI.
- All auth failure events (invalid token, expired token, revoked session) must be logged at
  WARN level without including the token value.

## Validation / follow-up

- Integration tests must cover: valid login, invalid credentials, expired token rejection,
  tampered signature rejection, refresh rotation (old token invalid after rotation),
  logout revocation, and suspended user rejection.
- Verify `golang.org/x/crypto/sha256` is used for token hashing (not a weaker hash).
- Verify `crypto/rand` is used for refresh token generation (not `math/rand`).
